# 进阶实战：性能调优与大规模媒体库优化指南

大媒体库先分清耗时发生在云盘扫描、STRM 写入、元数据下载、媒体服务器扫描还是客户端播放。不能用固定内存、并发或“万条几十秒”推断所有部署的表现。

> 配置入口与行为核对日期：2026-11-17。以下为项目机制与排查方法，不是百万级规模或第三方客户端的实测承诺。

## 1. 先读统计，再调整并发

- **STRM 同步**查看扫描目录、云端请求与重试、延迟分位、生成 / 跳过数和各阶段耗时。快速同步处理变化队列，完整校准遍历配置来源，两者工作量不同。
- **媒体反代 → 播放链路记录**区分云盘直连（302）、MF 转发及 HLS。展开 `PlaybackInfo` 看上游与 MF 内部耗时；signed URL 缓存命中不代表上游播放协商也会变快。
- **日志记录 / 本地媒体**查看识别等待、跨盘复制、待确认与后处理。跨盘吞吐和共享挂载延迟通常与本机重命名不同。

并发应根据限流、错误率和磁盘负载小步调整，不以增加扫描线程代替减少扫描范围。项目的索引和缓存减少重复工作，不保证每个阶段都不访问磁盘或云盘。

## 2. 数据库与存储

数据库位置随部署布局确定；默认 Docker 把宿主机 `./data` 挂到 `/app/db`，数据库为 `/app/db/mediaflux.db`。不要在错误工作目录连接相对路径，SQLite 可能悄悄新建空库。

需要检查时，可在 **MediaFlux 容器终端**只读查询已有数据库：

```bash
python - <<'PYDB'
from pathlib import Path
import sqlite3

path = Path('/app/db/mediaflux.db')
if not path.is_file():
    raise SystemExit('数据库不存在，请先核对实际部署路径')
connection = sqlite3.connect(path.as_uri() + '?mode=ro', uri=True)
try:
    print('Journal mode:', connection.execute('PRAGMA journal_mode').fetchone()[0])
finally:
    connection.close()
PYDB
```

应用连接会协商 WAL 并设置忙等待；WAL 减少读写互相阻塞，但不消除 SQLite 的写入竞争。不要为常规调优直接在运行中的生产库执行 `VACUUM` 或手改索引。需要维护时先做一致性备份、安排停服窗口，再核对实际收益。

把数据库与缓存放在可靠的 SSD 可减少机械盘随机访问，但 STRM、海报、字幕和媒体服务器自身仍有磁盘 I/O，不能保证机械盘始终休眠。STRM 文件虽小，也有目录、文件系统分配和伴随元数据开销。

## 3. 控制扫描范围并保持路径稳定

1. **选择实际归档来源**，不要为了扫描方便同时加入互相重叠的父子目录。光鸭根目录 ID `0`不能作为 STRM 来源。
2. 来源固定输出到 `STRM_ROOT/光鸭云盘/来源隔离目录/…`，不随来源个数平铺或加层。保持 `STRM_ROOT`、来源 ID 与媒体库挂载稳定，避免不必要的全量重建和重扫。
3. 整理联动和快速同步处理已知变化；外部手动改名、删除或内容变化仍需完整校准发现。播放地址变更后，也要完整校准改写旧 STRM。
4. 完整校准的 Cron 默认 `0 4 * * *`，但须启用对应定时任务；按更新量与限流情况调整，不要盲目每几分钟遍历整库。RSS 另按订阅的分钟周期调度，不共用这个 Cron。
5. 在完整校准报告扫描异常时先处理原因，不绕过清理保护强行删除本地镜像。

## 4. 减少刷新放大与播放中转

在 **媒体库与路径映射**中对应 MF 输出路径与媒体服务器实际路径。自动刷新合并本轮变化：电影定位自身，剧集优先整剧以更新汇总日期，无整剧条目才退到单集、季或目录；新作品必要时扫描所属物理根或库，不扩大到无关全库。

普通扫描采用默认元数据 / 图片刷新模式，补齐缺失内容；强制覆盖属于另行发起的刷新模式。无法匹配或请求失败时 MF 记录告警并结束本次自动处理，由用户在媒体服务器手动刷新，不会周期性重放旧路径。去重窗口中的新变化会延后，避免丢失更新。

播放端只有实际媒体 GET 被重定向到 CDN，持续视频流量才绕过 MF。MF 转发承载原始流，HLS / 转码还涉及媒体服务器，均应按真实带宽与设备能力评估。不同客户端、文件和网络环境需分别核验，不承诺统一起播时间或必然 302。
