# MediaFlux 部署指南


## 1. 下载 Compose 配置

创建运行目录并下载官方 Compose 文件：

```bash
mkdir -p mediaflux && cd mediaflux
curl -fsSL https://raw.githubusercontent.com/li88iioo/MediaFlux/main/docker-compose.yml -o docker-compose.yml
```

---

## 2. 修改挂载路径

编辑 `docker-compose.yml` 中的 `volumes`，将冒号左侧替换为宿主机实际路径：

```yaml
volumes:
  - "./data:/app/db"               # 数据库、配置、缓存与日志（保持默认即可）
  - "./strm:/data/strm"            # STRM 生成文件输出目录
  - "/volume1/downloads:/media/downloads"  # 下载目录（对接 qBittorrent/下载器）
  - "/volume1/media:/media/library"        # 媒体库目录（本地整理与归档目标）
```

挂载目录说明：

| 宿主机路径（左侧按需修改） | 容器内路径（右侧固定） | 说明 |
| :--- | :--- | :--- |
| `./data` | `/app/db` | 系统配置与 SQLite 数据库 |
| `./strm` | `/data/strm` | 网盘生成的 STRM 文件目录 |
| 宿主机下载目录 | `/media/downloads` | 待整理的下载目录 |
| 宿主机媒体目录 | `/media/library` | 本地归档目标与媒体库目录 |

> **注意**：进入 Web 页面配置下载目录或整理规则时，路径必须填写**容器内路径**（例如 `/media/downloads`），不要填写宿主机的实际路径。

---

## 3. 启动与初始化

执行启动命令：

```bash
docker compose up -d
```

启动后在浏览器中访问：

```text
http://<服务器IP>:1258/setup
```

根据页面提示创建管理员账号即可完成初始化。系统会自动生成安全密钥并写入 `./data` 目录。

日常管理命令：

```bash
# 查看容器状态
docker compose ps

# 查看实时日志
docker compose logs -f mediaflux
```

## 4. 网络模式配置

### 默认 Host 模式（推荐）

Compose 默认配置为 `network_mode: host`：
- Web 服务固定监听宿主机 `1258` 端口；
- 在 Web 控制台新增媒体反代实例并指定端口（如 `18096`）后，宿主机对应端口会直接生效，无需修改 Compose 重启容器；
- 请确保配置的端口未被宿主机其他服务占用。

### Bridge 桥接模式

如需使用 Docker 桥接网络并自定义端口映射，删除 `network_mode: host`，并配置 `ports`：

```yaml
    # network_mode: host
    ports:
      - "0.0.0.0:111:1258"    # 宿主机 111 -> Web 1258
      - "0.0.0.0:222:18096"  # 宿主机 222 -> 媒体反代 18096
```

> **注意**：媒体反代映射的容器内端口（右侧）必须与 Web 页面中反代实例填写的监听端口一致。如果页面中填写的是 `1234`，宿主机希望使用 `222`，则应写为 `222:1234`。

## 5. 权限说明

容器默认以 NAS 兼容模式（root）运行，仅访问 Compose 明确挂载的目录；这能兼容多数本地磁盘与 NAS ACL，通常无需手动 `chown`。NFS root squash 或宿主机 ACL 仍可能拒绝删除，此时应改用下方固定 UID/GID 模式，并让该身份获得目录权限。

如需指定非 root 用户运行，可在 Compose 中添加环境变量：

```yaml
    environment:
      MEDIAFLUX_RUN_AS_ROOT: "0"
      PUID: "1000"   # 改为宿主机文件所有者 UID
      PGID: "1001"   # 改为宿主机文件所属组 GID
      UMASK: "022"
```

权限契约如下：

- `/app/db` 是 MediaFlux 自有数据。首次使用某组 PUID/PGID、或 PUID/PGID 发生变化时会递归迁移一次；后续启动不会重复扫描整棵目录。
- `/data/strm` 默认只修复挂载根目录。确需迁移已有 STRM 文件所有权时，临时设置 `MEDIAFLUX_FIX_STRM_PERMISSIONS: "1"`，成功启动一次后删除该变量。
- `/media/downloads` 与 `/media/library` 属于用户业务数据，入口脚本**永不递归改权**。PUID/PGID 必须由宿主机所有权或 ACL 授予读、写、移动与删除权限。
- 如需重新修复 `/app/db`，临时设置 `MEDIAFLUX_FIX_DATA_PERMISSIONS: "1"`，成功启动一次后删除该变量。
- 不要同时配置 Compose 的 `user:` 与 `MEDIAFLUX_RUN_AS_ROOT=0`；`user:` 会让入口脚本失去调整容器用户和目录的权限。

可用 `id economic` 或 `stat -c '%u:%g %n' <目录>` 查询宿主机 UID/GID。指定 PUID/PGID 后，如果本地媒体只能读取但无法删除，通常是目录缺少写权限，而不是 MediaFlux 的删除逻辑问题。

## 6. 版本升级与数据备份

普通升级与容器重启应完整保留数据库、配置、Token、STRM 和整理任务数据，不要删除或重新初始化挂载卷。先准备并校验备份，再升级镜像；回退不是只把镜像标签改回旧版。

### 6.1 升级前准备与备份校验

- 阅读 [CHANGELOG](../CHANGELOG.md) 中目标版本的升级说明，核对完整数据库 schema 跨度和功能兼容边界。**0.1.12 的 schema 迁移跨度、旧 Agent 对话与待确认操作兼容边界，以该版本「升级说明」为权威**，本指南不另行复制版本特有规则。
- 记录当前运行版本、commit 和 Compose 配置，保留可用的旧版精确镜像标签或 digest；`latest` 是浮动标签，不能作为回退版本记录。

```bash
# 记录升级前的运行版本和构建信息
docker compose exec mediaflux python mediaflux.py version --json

# 创建数据库、配置和 Token 备份；命令输出备份 ZIP 的绝对路径
docker compose exec mediaflux python mediaflux.py backup create --reason manual

# 查看默认备份目录（CLI 只有 create / verify / restore，没有 list 子命令）
docker compose exec mediaflux sh -lc 'ls -lah /app/db/backups'
```

将下面 `BACKUP` 替换为刚才输出的实际路径（使用容器内路径；默认对应宿主机 `./data/backups`），不要直接使用占位文件名：

```bash
BACKUP='/app/db/backups/请替换为实际备份文件名.zip'
docker compose exec mediaflux python mediaflux.py backup verify "$BACKUP" --json
```

`verify` 会核对归档条目大小、SHA-256 哈希、SQLite 完整性与外键，以及实际 schema 与 manifest 是否一致；校验失败时先解决备份问题，不要继续升级。还应检查输出的 `entries` 是否包含 `database/mediaflux.db` 及应有的配置、Token，确认 `database_schema_version` 属于升级前版本。

> **备份范围**：CLI 只打包实际存在的 SQLite 数据库、`user.env` 与 `guangya_token.json`，数据库内的整理任务随库保留；它不是整个 `./data` 的镜像，也不包含 STRM、下载或媒体文件。完整目录备份与整机迁移见第 6.4 节。将备份另存到数据卷之外的安全位置并限制访问权限，其中可能包含凭据。

首次启动新版本时，程序会在 schema 迁移前自动创建备份；这不能代替升级前的人工备份和完整数据目录保留。自动备份同样需要通过 `backup verify` 校验。演练或故障注入只在隔离数据副本上进行，不要使用真实生产数据卷。

### 6.2 升级镜像

确认第 6.1 节备份可用后，先停止旧服务；此时可按第 6.4 节保留一致的完整目录副本：

```bash
docker compose stop mediaflux
```

将 `docker-compose.yml` 中的 `image:` 改为选定的目标精确版本；保持原有挂载路径、权限与环境配置不变。若目标版本支持下述 `runtime-migrate` 命令，首次从平铺锁布局升级时，在启动前完成一次离线收纳：

```bash
docker compose pull mediaflux
# 仅对支持 runtime-migrate 的目标版本执行；失败时不要继续启动
docker compose run --rm --no-deps --pull never mediaflux \
  python mediaflux.py runtime-migrate
```

迁移成功后再启动（已经完成迁移或全新数据目录可直接启动）：

```bash
docker compose up -d mediaflux
```

**运行文件布局**：普通跨进程锁收纳到各自数据命名空间的 `runtime/locks/`，PID 在数据目录的 `runtime/mediaflux.pid`。Docker 默认平铺数据目录下的大多数锁因此集中到 `/app/db/runtime/locks/`；Agent 计划目录内的锁保留隔离范围，放在相应目录的 `runtime/locks/`。根目录只保留 `.mediaflux-runtime-lifecycle.lock` 作为新旧版本共同的唯一启动互斥点，不能删除。

- 迁移前停止所有使用同一数据目录的服务、备份工具及自动拉起任务，迁移期间不要启动旧版本。程序会检查生命周期锁与旧/新操作锁；发现占用则拒绝迁移。
- 命令只收纳锁并清理停服后的陈旧 PID，不移动数据库、`user.env`、光鸭凭据、Agent 计划、日志或备份。新 PID 在下一次启动时写入；锁文件不代表当前有活跃任务，不按数量做垃圾清理。
- 命令可重复执行；中途失败时保持停服，排除原因后重跑。发现旧锁的新版本会明确提示迁移，不在运行中悄悄切换锁位置。
- 源码部署使用 `.venv/bin/python mediaflux.py runtime-migrate`，须与 `start` 使用相同环境变量和 `--data-dir` 配置。禁止在运行中的实例目录里手工搬锁、清锁。
- 回退旧版本需先停止新版本并遵循下节的数据恢复流程；旧版会重新产生平铺锁，之后再升级需要重新执行本命令。

等待初始化和迁移完成，检查运行版本、诊断结果及日志，并确认历史配置、任务与文件可用：

```bash
docker compose exec mediaflux python mediaflux.py version --json
docker compose exec mediaflux python mediaflux.py doctor --json
docker compose logs --tail=100 mediaflux
```

如果升级失败，不要反复切换镜像尝试打开同一数据库；需要回退时使用下一节的离线流程。

### 6.3 离线恢复与安全回退

**恢复会覆盖当前数据库，以及备份内包含的配置和 Token；恢复后的状态回到备份时间点，备份之后的变更不会自动保留。** 先停止服务并另存当前数据目录用于排查，再恢复已验证的升级前备份。数据库备份不能撤销云端或媒体文件变化，相关文件仍需按实际状态核验。

1. **先停止新版本及所有共用该数据目录的实例**，确认没有其他进程写入或自动拉起服务：

   ```bash
   docker compose stop mediaflux
   ```

2. **只运行离线 CLI，不启动应用服务**。保持相同数据挂载和权限配置，将 Compose 的 `image:` 固定为本地已有、支持该备份格式与 schema 的恢复工具镜像（可使用当前新版的精确版本或 digest）。下面的 `run` 显式覆盖默认启动命令；`--no-deps` 不启动依赖，`--pull never` 不临时拉取浮动镜像。不要使用需要运行中容器的 `docker compose exec` 来做离线恢复。

   将 `BACKUP` 替换为第 6.1 节已校验的**升级前**归档路径；若换了终端，也要重新设置该变量。先单独执行 `verify`，仅在成功后执行 `restore`：

   ```bash
   BACKUP='/app/db/backups/请替换为升级前的实际备份文件名.zip'
   docker compose run --rm --no-deps --pull never mediaflux \
     python mediaflux.py backup verify "$BACKUP" --json
   ```

   ```bash
   docker compose run --rm --no-deps --pull never mediaflux \
     python mediaflux.py backup restore "$BACKUP"
   ```

   `restore` 会再次验证同一批归档内容，拒绝运行中恢复、缺少数据库的完整恢复，以及高于执行该 CLI 的程序所支持 schema 的备份。命令失败时保持停服并排查，不要绕过校验；确认数据库及所需配置、Token 都已恢复到升级前的一致状态，缺失项须从对应完整目录副本补齐后再继续。

3. **恢复成功后，先将 Compose 的 `image:` 改为升级前记录的旧版精确版本或 digest，再启动旧版本**。若本地缺少该旧镜像，保持停服，在固定旧版引用后拉取并核对它；不要改回 `latest`。确认镜像已在本地后执行：

   ```bash
   docker compose up -d --no-deps --pull never mediaflux
   docker compose exec mediaflux python mediaflux.py version --json
   docker compose exec mediaflux python mediaflux.py doctor --json
   docker compose logs --tail=100 mediaflux
   ```

   核对实际运行版本及历史数据。**禁止让旧程序直接打开更高 schema 的数据库；恢复后也不要先启动新版本，否则会再次触发升级。**

### 6.4 完整目录备份与整机迁移

迁移到新设备或保留完整回退副本时，先停止 MediaFlux 及其他可能写入这些目录的进程，再打包保留以下内容，避免直接复制运行中的 SQLite 文件造成不一致：

- `docker-compose.yml` 及自行维护的环境配置文件；
- `./data` 完整目录（数据库、配置、Token、备份、缓存与日志），而不只是 CLI 备份 ZIP；
- `./strm`（STRM 文件）；
- 本地下载与媒体文件。

保留文件权限，按新设备实际路径调整 Compose 挂载，但保持容器内路径契约一致；先用与备份匹配的版本验证数据可用，再按本章升级。恢复备份的具体步骤沿用第 6.3 节，不能用启动新版本代替离线恢复。

## 7. 常见问题

### 无法访问 Web 页面
1. 执行 `docker compose logs -f mediaflux` 确认容器是否正常运行；
2. host 模式下确认 `1258` 端口未被其他服务占用；
3. 检查系统防火墙或安全组是否放行了 `1258` 端口。

### 仅使用云盘 STRM 功能
如果不需要本地下载与文件整理功能，可直接在 Compose 中删除 `/media/downloads` 与 `/media/library` 两行挂载，仅保留 `./data` 和 `./strm`。

### 公网访问与反向代理
如需通过域名访问，建议使用 Nginx 或 NPM 反代至内网 `http://127.0.0.1:1258`，需注意：
- 开启 WebSocket 转发支持（日志推流与实时状态）；
- 开启 SSE（Server-Sent Events）长连接支持；
- 关闭对动态 API 路径的静态缓存。
